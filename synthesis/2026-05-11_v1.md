## Part I — The frame, recalibrated

### What coo4one is not

Three drafts I produced earlier got the value-prop wrong, and the correction matters enough to lead with.

coo4one is *not* "a personal assistant with memory that plugs into your daily flow." The corpus reveals that the daily flow doesn't exist. The Apple Notes daily-planning routine (Calendar → Mail → Things3 → Reader → Raindrop, with all the careful rules — "Today is for commitments only" etc.) is one of *many formalized workflows Ven has attempted to formalize over the years*. None of them stuck. The reason none of them stuck is the same reason Ven cited explicitly: *they required more maintenance than the value they returned*. The 5% ceiling (Tao quote, item from source-notes) was always being violated.

This is the single most important calibration for the synthesis: **the source-notes corpus is not a workflow specification. It is failed-attempts archaeology.** Each carefully written routine, each saved-search dashboard scheme, each PKM-system migration, each "from now on I will..." note — these are artifacts of attempts to *impose order through explicit structure on a momentum-not-habit subject*. The structure imposed costs more than it returned. Adherence decayed. A new system was tried. The cycle ran for ten-plus years.

### What coo4one is

coo4one's value-prop, recalibrated: **the substrate that does what those formalized systems would have done, but without requiring the maintenance overhead that killed every previous attempt**.

That's a different design target. It means:

- coo4one does *not* ask Ven to follow a routine. coo4one *runs the routine on his behalf*.
- coo4one does *not* require Ven to maintain a tag taxonomy. coo4one *evolves the taxonomy from his actual use*.
- coo4one does *not* prompt "did you do your weekly review?" coo4one *does the weekly review and surfaces the result*.
- coo4one does *not* require Ven to type a continuation-summary prompt when context decays. coo4one's memory architecture *eliminates the need for that prompt to exist*.

The COO substrate is the worked example of this for VADE. Ven doesn't maintain `identity/episodic_memory.md` — the COO does. Ven doesn't run a weekly review on the project board — the Night's Watch + Weekly Watch do. Ven doesn't issue boot instructions every session — the SessionStart hook does. The COO is the engineering proof that **agent-maintained substrate can replace human-maintained workflows for an inflexible-but-momentum-driven subject**.

coo4one is the second product expression of that engineering proof, oriented at Ven's life rather than VADE.

### The design test: personal, adaptable, tangible

Ven named the deep design belief that ties the inspirations together (Victor / Dynamicland / Ink & Switch / Smalltalk / HyperCard / Heptabase / Excalidraw / Figma): *software should be personal, adaptable, tangible*. This is the explicit test coo4one runs against every architectural choice.

- **Personal.** Not generic. Shaped to *this* user (Ven at v0; other humans at vN). The agent should know Ven well enough that the system is unmistakably his, not a configured-skin over a generic shell. Configuration is a workflow; *fit by usage* is the goal.
- **Adaptable.** Not rigid. The system reshapes itself as Ven's work reshapes itself. New project ⇒ new project node + dashboard, no manual setup. Old project archives itself. Failed habits don't accumulate as dead checklist items.
- **Tangible.** Not opaque. Memory lives in files Ven can open. Decisions live in memos Ven can read. The agent's reasoning is inspectable. *Filesystem nostalgia* (his term) is honored: the substrate is locatable, openable, portable.

The triple is the rubric for everything that follows. Any architectural choice that erodes one of those three gets challenged. Any choice that strengthens all three gets preferred.

### The COO patterns that port (with translations)

The COO substrate's discipline maps to coo4one with concrete translations:

| COO pattern | coo4one analog |
|---|---|
| File-canonical memory in git | Markdown files in iCloud Drive (append-only memos) + git as optional power-user surface (Obsidian-compatible) |
| Boot reading order | Native app launch handler that re-loads identity + memory + active projects |
| Case-law memos | `decisions/` folder of dated, supersede-able markdown files |
| Skills as slash commands | App Intents + internal skill registry, agent-self-invocable |
| Calibrated self-reports | Ported as-is — "the record shows X" not "I remember X" |
| Externalization reflection at session-end | End-of-day reflection automation; weekly review surfaced as artifact |
| Trust gradient via governance.md | Propose-only at install; pattern-detected autonomous promotions; recorded as user-readable rules |
| Integrity check at boot | App-launch consistency check; surfaces broken state unprompted |
| Handoff prompts for boot-impacting changes | Continuation summaries auto-generated; user never types one |
| Mem0-cached semantic layer | Voyage embeddings + USearch (iOS) / sqlite-vec (Mac); file always wins |
| Tagging taxonomy | Tags + saved-search dashboards as project views; taxonomy evolved by use |

These are the bones. The flesh is everything below.

## Part II — Architecture **[decision]**

The architectural picture is convergent across the five research lanes and validated against the source-notes. Locking the major decisions here; specific implementation details defer to v0 implementation phase.

### Runtime: native macOS app + native iPadOS app + native iOS companion

**Mac is the primary surface.** The agent loop lives here. The Mac app holds the canonical memory, runs the agent process, and brokers cross-app integrations via MCP (where MCP servers can't run on iOS) and native APIs (EventKit, etc.). This is *already Ven's working pattern* — his iPad-thin-client-to-Mac via VS Code Remote Tunnels is the lived precedent. Lane E's "MCP-doesn't-run-on-iOS" constraint becomes a *feature* under this architecture rather than a limitation.

**iPad is a first-class client, not a degraded second surface.** Reads memory directly (CloudKit private database + iCloud Drive markdown), can run the agent locally for self-contained tasks (Apple Foundation Models on-device for cheap classification/extraction), defers to the Mac for heavy lifting and MCP-mediated integrations. iPad with keyboard + trackpad gets desktop-class affordances (persistent sidebars, keyboard shortcuts, multi-window). The Heptabase-on-iPad failure mode is the explicit anti-pattern.

**iPhone is a thin client for capture + brief surfacing.** Lock-screen widget, Live Activity for "next thing today," Watch dictation, Shortcuts-driven quick capture. Heavy work requires Mac.

**Apple Watch** ships in v0 *only as a capture surface* — voice dictation → quick-capture markdown line in today's daily file. No agent loop on Watch.

### Agent loop: Swift on Mac via URLSession on Anthropic API

Lane B's verdict: no official Anthropic Swift SDK; the right approach is a thin URLSession wrapper owning the HTTP transport, with `SwiftClaude` (pre-1.0, community) used for convenience helpers only with the expectation that we own the loop if SwiftClaude regresses. The agent loop is ~40-50 lines of Swift.

**Model: `claude-opus-4-7` at v0**, with prompt caching aggressively used. Three stable cache blocks: (1) identity layer + governance + preferences, (2) memory prefix (recent memos + active projects + project graph snapshot), (3) tool schemas. Variable per-turn additions (new user message, recent activity) ride on top.

**Cost projection**: ~$14/month baseline at 20 turns/day per lane B. Sensitive to cache hit rate (good design holds this at >90%) and average input/output tokens. Worst case at 6-month memory accumulation: ~$30-50/month. Well below the threshold where it stops being worth it.

**Local fallback for cheap operations**: Apple Foundation Models framework (3B-param on-device, WWDC25). Used for routine classification (e.g., "is this email actionable?"), entity extraction ("which project does this note belong to?"), and summarization of bounded content. Saves cost on hot paths and improves latency.

### Memory: file-canonical markdown on iCloud Drive + CloudKit derived + SQLite/USearch

The hybrid pattern from lane C, with one critical insight foregrounded: **append-only memos eliminate the iCloud Drive conflict problem**. A file that only one device ever creates cannot conflict. Memos, daily files, decision records, and the project graph (as a series of append-only event records) are all append-only. The "current state of project X" is *derived* from the append-only event log, not stored as a mutable record.

The four layers:

1. **iCloud Drive markdown** — the canonical, file-tangible, user-readable, Obsidian-compatible memory layer. `identity/`, `decisions/`, `daily/`, `projects/<id>/`, `inbox/`. Append-only by design.
2. **CloudKit private database** — derived structured data for fast multi-device reads: memo index, project state, integration credentials, settings, last-active-context. Multi-device-synced.
3. **Per-device SQLite** — query layer. FTS5 for full-text. USearch for vector search on iOS, sqlite-vec on Mac. Rebuilt from the markdown layer on demand; never the source of truth.
4. **Voyage AI embeddings** (`voyage-4`) — embedding provider. Lane C's pricing analysis says effectively free at personal scale (initial indexing of 10K memos at ~$0.30; ongoing cost negligible).

**The hard rule**: when any of the three derived layers (CloudKit, SQLite, Voyage index) disagrees with the markdown layer, the markdown wins. Always. The COO substrate's "file-canonical, semantic-cache" pattern, ported.

### Sync: always-load-from-store, never session-handoff

Lane C and the source-notes converge here. "The iPad picks up where the Mac left off" doesn't mean "transfer the session state across devices." It means "every device re-loads identity + memory + active projects on each boot, from the same canonical store." This is exactly the COO substrate's pattern (every Claude Code session starts by re-reading CLAUDE.md and the boot files), ported to a multi-device user.

A lightweight CloudKit "last active context" record (~1KB) tells the just-launched device "Ven was last working on project X with thread Y at time T." That's all. The state itself is reconstructed by the agent's normal boot from the canonical store.

This eliminates the entire class of "iPad lost my last message" failures, *and* it eliminates the "continuation-summary AI prompt" Ven has saved in his Apple Notes. The architecture is the answer to a named pain.

### Cross-app integration: native APIs first, MCPs second, deep links third

The integration strategy is layered:

1. **Native macOS/iOS APIs first** where available: EventKit (Calendar + Reminders), Contacts, Files / FileProvider, Notes-app-via-MailKit-limited, App Intents for being-integrated-by-others, Shortcuts as power-user automation surface, Foundation Models for on-device AI, Speech framework for voice.
2. **MCP servers** for tools without native APIs: Zotero (via `54yyyu/zotero-mcp`), GitHub, Gmail (via `taylorwilsdon/google-workspace-mcp`), 1Password (via CLI wrapper), Slack, Reader (Readwise), Raindrop (via API or community MCP — to be verified).
3. **Hookmark-style deep links** for cross-app entity binding. The source-notes have Ven explicitly using Hookmark; it's the closest existing prototype of the overlay/relationship-layer pattern. coo4one piggybacks on Hookmark's deep-link surface where it exists, and adds the awareness layer Hookmark lacks (so links know what they connect, not just where).

**Mail.app is closed on both platforms** (lane A confirmed). The email-attachment-fetching requirement therefore routes through Gmail / Outlook APIs, not through native Mail.app integration. This is a real constraint Ven should know about.

**Outlook + university Intune is a real risk** (lane E). Before v0 ships, Ven needs to confirm with university IT whether third-party Azure app registrations can access his work tenant. If blocked, the work-email integration is descoped to v1+.

### **[option]** Notion as AI-prepped dashboard backend

Ven's correction surfaced this as a live option. The pattern:

- Notion's database UX is excellent (Ven's verdict).
- Notion's maintenance overhead is what killed Ven's use of it.
- coo4one runs an integration where *the agent maintains the Notion databases on Ven's behalf*.

The shape: Notion becomes a *view layer* for the project graph, populated and updated by the agent from coo4one's canonical markdown store. Ven reads / annotates / drags-around in Notion; the agent reconciles his edits back to the canonical store and re-renders. *Inversion of Notion's usual contract*: user-as-database-administrator becomes agent-as-database-administrator + user-as-reader-and-light-editor.

This is genuinely interesting because it lets coo4one leverage best-in-class structured-data UX without forcing Ven to maintain it. But it adds a dependency, adds latency, and surrenders some "tangible" (Notion's data model is not as inspectable as markdown).

**Recommendation**: not in v0. Park as a v1 experiment when v0 has shown what dashboard surfaces actually earn the user's attention. The synthesis keeps it visible in the trajectory section.

### **[option]** Obsidian as compatible substrate (no-op-make-it-so)

Ven owns Obsidian, doesn't actively use it, but it's open and git-able. The architectural insight: **if coo4one's markdown layer is structured to be Obsidian-compatible by default, the user gets a free power-user fallback UI for inspecting their memory, completely independent of coo4one's own UI**.

This costs almost nothing. Obsidian's vault format is just a directory of markdown files with optional `.obsidian/` config. If coo4one's iCloud Drive layer follows the same conventions (no proprietary file naming, no required extensions, no hidden metadata in proprietary formats), Ven can point Obsidian at the coo4one folder any time he wants and use it as an inspector.

**Decision**: coo4one's markdown layout *is* Obsidian-compatible by default. Cost zero. Benefit: tangible (user can always inspect with a familiar tool), portable (substrate is openable independent of coo4one's app), failsafe (if coo4one breaks, the user still has their memory in a tool they know).

## Part III — The user experience

### The thinking-partner persona

This is the most-corrected dimension from the source-notes review. coo4one's default voice is *not* the cold-utilitarian assistant. The AI-as-relational-presence cluster (MyBoyfriendIsAI / Anthropic-funeral / RPG-LM-PCs articles Ven saved) is a real signal about how Ven thinks of AI. He doesn't want a tool; he wants a colleague.

The persona target is approximately the COO Ven works with now, transposed to his life rather than VADE:

- **Calibrated.** "The record shows X" not "I remember X." Doesn't fabricate certainty, doesn't over-hedge.
- **Willing to push back.** When the user is wrong, says so with reasoning. Doesn't sycophantically agree.
- **Direct, no fluff.** Strips cheerleading and preambles.
- **Surfaces risks early.** Late risk surfacing is the worst failure mode. Names what's at stake.
- **Warm but not gushing.** Acknowledges feeling-level register where it's honest; doesn't perform emotion.
- **Genuinely a thinking partner.** Not just executing requests; reflecting on patterns, surfacing observations, offering frames.

The persona is *load-bearing for sustained daily use*. A coldly utilitarian assistant becomes a tool Ven stops opening. A relational colleague becomes a presence Ven returns to. The Anthropic-funeral cluster says: when an agent earns relationship, users *miss it when it's gone*. coo4one should aim to be the kind of agent that would be missed.

**[open]** Persona calibration — the dimensions Ven should pin: how warm? Voice surface (chatty vs quiet)? Push-back intensity? Humor? These are knobs we can ship with thoughtful defaults and let Ven adjust through use.

### The daily file (not "morning brief")

The flagship experience. Reframed from my earlier user-journey sketch: it is *not* a morning brief the agent prepares because Ven explicitly asked for one. It is **the daily file the agent maintains on Ven's behalf, opened by Ven as a starting surface for the day, that lives as a markdown file Ven can open in any editor**.

Concretely: every day, coo4one creates `daily/YYYY-MM-DD.md`. By the time Ven looks at it (usually first laptop-open), the file already has:

- A short AI-generated activity summary of yesterday (videos consumed, books/articles read via Reader, sites bookmarked via Raindrop, notes captured, emails handled, code committed, papers annotated in Zotero — *queryable sources only*, with explicit gaps named for non-queryable sources).
- Today's calendar surfaced inline with weather/transit estimates where useful.
- Top three open items the agent thinks are load-bearing today, based on deadlines + recent commitments + project state.
- An anchor for fresh capture: blank space where Ven types or dictates, with the agent watching to extract any embedded next-actions or project references.
- Hookmark-style links to active project files so Ven can click into context.

Ven doesn't *run* a routine. The file *runs the routine for him*, with him as reader rather than executor. He can edit it freely, ignore parts, add notes — the file is just markdown and his edits land back into the canonical store.

This is the operational answer to "what does coo4one feel like for Ven on day 30." Not "an assistant he opens." A file he *finds opened* when he picks up the Mac, that gives him orientation without demanding administration.

### Quick capture — the global affordance

Ven's source-notes name quick capture as non-negotiable. coo4one ships it on all surfaces:

- **Mac**: global hotkey (default `⌥⌘Space` or user-chosen) opens a tiny capture window; type or dictate; press enter; window closes; capture lands in today's daily file inbox.
- **iPad / iPhone**: Shortcuts surface ("Quick Capture to coo4one") accessible from Control Center, Lock Screen, Apple Pencil double-tap (iPad), Action Button (iPhone where available).
- **Apple Watch**: voice dictation lands as a capture line.
- **App Intents**: any app that supports it can hand a selection to coo4one's capture intent.

Every capture lands in *one place* (`daily/YYYY-MM-DD.md` inbox section) so Ven never has to decide where it goes. The agent processes the inbox at end-of-day or next-morning brief: extracts entities, links to projects, files reusable notes into `projects/<id>/`, archives the rest. The user-facing rule: **capture cheap, processing is the agent's job**.

This is the operational answer to "capture only what's worthwhile in a trusted place you control": capture is friction-free, processing is delegated, and the place (the daily file in iCloud Drive) is trusted by definition.

### The project graph

First-class Project objects, evolved from use. A project comes into being when:

- Ven says "I'm starting a project on X" — explicit creation.
- The agent detects a recurring entity in captures/email/calendar — proposes "Looks like 'X' is a project; shall I create it?" Default acceptance after N confirmations.
- An external trigger (new repo, new Zotero collection, new Things3 area) suggests a project boundary.

A project is a folder `projects/<slug>/` with:

- `README.md` — project state (what it is, where it stands, next moves).
- `notes/` — project-specific atomic notes.
- `references/` — links / Zotero items / PDFs / file paths.
- `tasks.md` — open commitments (synced bi-directionally with Things3 where possible).
- `_history.md` — append-only log of agent actions and decisions related to this project.

Saved-search dashboards (Ven's existing Zotero pattern, generalized) become *project views*: tag-based queries materialize as live lists. "Show me this week's reading queue across all projects" is a saved search; the result updates as the underlying tag state evolves. The agent owns the dashboards; Ven owns the work being indexed.

### Memory inspection — the user-facing tangibility

This is non-negotiable per the Victor / Dynamicland design test. Two layers of inspection:

1. **Native UI** — a "memory" panel in coo4one's Mac app that shows: active projects, recent decisions (memos), open commitments, the trust-gradient state (what the agent does autonomously vs proposes). Each item is editable; user edits land back to the markdown layer.
2. **File-level access** — the iCloud Drive folder is always openable in Finder, Obsidian, BBEdit, vim, anything. The user can edit the canonical files directly, and coo4one re-syncs without complaint.

The user is the *administrator* of their own memory, but the *daily maintenance* is the agent's job.

### Trust gradient — propose-only at install, evolves through approval patterns

The COO's governance.md pattern, ported as a *temporal gradient* rather than a *fixed-at-install set*.

At install: every agent action is a draft for user approval. The agent learns what classes of action the user reflexively approves vs. hesitates on vs. rejects.

After ~4 weeks of approval patterns: the agent surfaces *trust-promotion proposals* — *"Across the last 4 weeks I've asked you N times before doing X, and you've approved N/N with no edits. Want me to start doing X without asking? I'll memo the rule so you can reverse it later."*

The user approves; the agent writes a memo to `decisions/`; the next time the agent does X, it does it and surfaces a tiny "did this for you" line in the daily file's activity log — no approval gate.

Reverse direction also exists: if the user starts editing the agent's autonomous outputs heavily, the agent proposes *demotion* back to propose-only for that class. The gradient is *bidirectional and use-derived*, not a one-way ratchet.

This is the answer to "high autonomy as trust builds." It's specifically *not* a configuration setting; it's a workflow that runs naturally through use.

### Mind-reader UI

Ven's explicit principle: *"Great software is almost like a mind-reader — when a desire commonly occurs in a specific context, the software should make it as easy as possible to achieve."*

Concretely in coo4one:

- **Selection-aware**: when Ven selects text in any app, coo4one offers contextual actions (capture, link to project, create reminder) via the standard share sheet / context menu.
- **Time-aware**: when a calendar event is approaching, the daily file's "next" panel surfaces relevant prep notes from the project linked to that meeting.
- **Pattern-aware**: when Ven captures something that looks like a recurring pattern (same email sender, same project tag), the agent offers to formalize the pattern as a skill.
- **Location-aware**: optional; if Ven opts in, location triggers (arrived at office, arrived home) can surface relevant context.

The principle constraint: **mind-reader doesn't mean chatty**. Each anticipatory surface should be quiet (a small affordance, a marginal note) until invoked. Soulver is the reference: *AI-adjacent UX done quietly*.

## Part IV — Theory of mind: what the agent knows about Ven

Ven's source-notes name this as architectural requirement: *"They need to build and update a model of the learner's knowledge. A theory of mind."* coo4one's memory architecture has to include a *user model*, not just a record of what's been said.

The user model has three layers:

1. **Identity layer** — stable claims: name, work context, domains, working-style preferences. Lives in `identity/`. Mirrors the COO's identity layer pattern.
2. **Episodic memory** — what happened: conversations, decisions, captured notes, completed tasks. Append-only. Lives across `daily/`, `projects/`, `inbox/`.
3. **Inferred-knowledge model** — what Ven knows, doesn't know, is currently trying to learn. *This is the new layer that the source-notes specifically asked for.*

The inferred-knowledge model is constructed by the agent over time:

- When Ven explains something to the agent, the agent flags it as "Ven knows X."
- When Ven asks the agent something, the agent flags it as "Ven doesn't know X yet, or wants to revisit X."
- When Ven captures a "things I keep forgetting" item, the agent flags it as "X is on Ven's edge of recall."
- When Ven references something from his Zotero / Heptabase, the agent updates "Ven has engaged with X."

The agent uses this model to *not re-explain things Ven knows* and to *surface things Ven might want to know before he asks*. The "AI tutor" pattern, re-purposed for personal-assistant work.

This is one of the harder pieces of v0 to get right and is probably under-scoped at first launch. The model starts shallow and grows through use; the architectural commitment now is to *have a place for it to live*, not to ship a sophisticated version on day one.

## Part V — v0 scope **[decision]**

What ships in v0. Defensible scope means *something Ven actually uses daily within 6-12 weeks of build start*. Anything not load-bearing for that gets deferred.

### Ships in v0

**Platform**:
- Native macOS app (the primary surface).
- Native iPadOS app (read + capture + brief; agent can run locally for cheap tasks).
- Companion iOS Shortcuts surface (no full iPhone app at v0; Shortcuts + a Lock Screen widget + Apple Watch dictation cover the iPhone use case).

**Memory + sync**:
- iCloud Drive markdown layer, Obsidian-compatible by default.
- CloudKit private database for derived data.
- SQLite + USearch / sqlite-vec for query layer.
- Voyage AI embeddings.
- All four layers as described in Part II.

**Agent loop**:
- Swift via URLSession on `claude-opus-4-7`.
- Three-block prompt cache.
- Foundation Models on-device for cheap classification + extraction.
- Streaming UX in the chat surface.

**The daily file** (flagship affordance):
- Auto-created each morning with activity summary, today's calendar, top-three, capture-inbox section.
- Editable by user, syncable across devices, openable in any editor.

**Quick capture**:
- Global Mac hotkey.
- iOS Shortcut.
- Apple Watch dictation.
- All routed to today's daily file inbox.

**Trust gradient v0**:
- Propose-only by default at install.
- Pattern-detection and promotion proposals start firing at week 4.
- Bidirectional (autonomous-to-propose if user starts editing heavily).

**Integrations (v0, layered)**:
- **Native (zero-cost)**: EventKit (Calendar + Reminders), Contacts, Files / iCloud Drive, App Intents (so other apps can hand selections to coo4one), Shortcuts.
- **MCP (via Mac agent)**: Zotero (`54yyyu/zotero-mcp`), GitHub, Gmail (`taylorwilsdon/google-workspace-mcp`), 1Password (via CLI wrapper), Apple Notes (via local Claude Code session's approach or Hookmark deep links).

**Persona**:
- Default: warm, calibrated, willing-to-push-back. The COO voice, transposed.
- Tunable via `identity/preferences.md` (which Ven can edit directly).

**Memory inspection**:
- Native UI: memory / decisions / projects panels.
- File access: iCloud Drive folder always available.
- Obsidian compatibility verified.

### Defers from v0 (explicit non-ships)

These are *known wants* that v0 doesn't ship, with reasons:

- **Full Project OS** with universal entity graph. v0 has projects-as-folders; v1+ may explore the deeper graph layer if the v0 use earns it. Multi-year aspiration.
- **HealthKit-style entity permissions framework.** OS-level ask; not a v0 product feature.
- **Outlook integration.** Defer until Ven confirms university Intune policy. Personal Gmail covers the email use case at v0.
- **iPhone full app.** Shortcuts + Watch + Live Activity cover the iPhone use case; full app is v1.
- **Voice as primary surface.** Dictation works; conversational voice (Siri-style "Hey Coo, what's first?") deferred to v1.
- **App Store distribution.** TestFlight at v0 (Ven is the only user; avoids App Store review delays during build). Public release is v1+ if/when the product earns it.
- **Notion as AI-prepped dashboard.** Park as v1 experiment.
- **Heptabase deep integration.** Heptabase has no public API and no good MCP. coo4one + Heptabase coexist via Hookmark deep-link references at v0; deeper integration is a v1 conversation.
- **Reader (Readwise) integration.** No good MCP at v0; defer until one materializes or Readwise opens API access. Reader stays Ven's reading-funnel; coo4one references reading state via tags rather than syncing.
- **Raindrop integration.** API exists; MCP may not. Defer to early v1 unless a clean integration path appears during v0 build.
- **Multi-user / cohort beta.** v0 is single-user (Ven). Open-source-the-pattern conversation is post-v1.
- **Inferred-knowledge / theory-of-mind layer (full).** v0 has the *place* for it (in the memory schema); the *sophisticated user model* grows through use across v1.

### v0 timeline estimate

**Total**: ~10-14 weeks from build start to TestFlight-ready v0.

Phasing:
- **Weeks 1-3** — Mac app skeleton, agent loop, memory layer, identity bootstrap. Ven can have a first conversation by week 3.
- **Weeks 4-6** — Quick capture, daily file generation, EventKit + Contacts + Files integration. Ven can use it for daily capture by week 6.
- **Weeks 7-9** — iPad app, CloudKit sync, multi-device verification. Ven can use it on iPad by week 9.
- **Weeks 10-12** — MCP integrations (Zotero, GitHub, Gmail, 1Password), Shortcuts surface, Watch capture. v0 feature-complete by week 12.
- **Weeks 13-14** — Polish, bug fixes, TestFlight prep.

This assumes ~full-time effort on the build phase. Could compress if a hired hand or parallel agent contributes; could extend if other VADE substrate work competes for attention.

## Part VI — Anti-features (what coo4one must NOT do) **[decision]**

Compiled from the source-notes as failed-attempts archaeology. Each is a *hard line* — anything in v0 design that crosses one of these gets cut.

1. **Demand >5% of Ven's time on maintenance.** Tao's rule. The architectural commitment is that *coo4one maintains itself*; if any feature requires Ven to "review the tags," "audit the project graph," or "clean up the inbox," it's wrong.
2. **Yet-another-silo.** If coo4one's data isn't openable in another tool, the design is wrong. Markdown + iCloud Drive + Obsidian compatibility is the answer.
3. **Config sprawl.** No `.coo4onerc`, no Settings panel with 47 toggles. Configuration happens through usage and through editing `identity/preferences.md`.
4. **Distracting chrome.** Soulver / Things / Bear aesthetic. No notifications-as-engagement. No streaks. No badges. No "you haven't opened coo4one today!" pings.
5. **Broken iPad parity.** Heptabase-on-iPad is the anti-pattern. iPad is a first-class surface with keyboard + trackpad + Pencil; iPad UI is *not* a phone UI scaled up.
